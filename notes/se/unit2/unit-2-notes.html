§ 1

Functional vs Non-Functional Requirements

A software requirement is a condition or capability needed by a user to solve a problem or achieve an objective. Requirements range from high-level abstract statements of service to detailed formal mathematical specifications.

1. Functional Requirements

Statements of services the system should provide, how the system should react to particular inputs, and how the system should behave in particular situations. (In some cases, they also state what the system should not do).

Example: "The system shall allow students to search for courses by department, course code, or instructor name."

2. Non-Functional Requirements (NFRs)

Constraints on the services or functions offered by the system. They include timing constraints, constraints on the development process, standards, security policies, and performance targets.

Classification Sub-Category Engineering Definition & Concrete Example
Product Requirements
(Constrain runtime behavior)		 Performance / Speed The system shall render search query results in less than 0.5 seconds under a load of 1,000 concurrent queries.
Reliability & Availability The system shall maintain an uptime availability of $99.9\%$, with Mean Time Between Failures ($\text{MTBF}$) $\ge 720\text{ hours}$.
Security & Usability All stored passwords shall be hashed using bcrypt (cost 12); user interface shall comply with WCAG 2.1 AA accessibility guidelines.
Organizational Requirements
(Constrain policies & processes)		 Development Standards All backend services must be written in Java 17 and follow the Google Java Style Guide with 80% test coverage.
Delivery & Operational The system must be containerized using Docker and deployable onto Kubernetes clusters.
External Requirements
(Arise from external factors)		 Regulatory / Privacy Patient medical data must comply with HIPAA regulations and GDPR data erasure guidelines.
Ethical / Legal The system shall not collect geographic location data without explicit, opt-in consent from the user.

Quantifying Non-Functional Requirements with Metrics

Vague non-functional requirements (e.g. "The system shall be user-friendly and fast") are impossible to verify. Engineers must translate them into measurable, quantifiable metrics:

Quality Property Verifiable Measurement Metric
Speed Processed transactions/second; response time to user input; screen refresh rate.
Size Megabytes of RAM; gigabytes of disk storage footprint; binary payload size.
Ease of Use Training time required for novices; number of help desk tickets/user/month.
Reliability Mean Time To Failure (MTTF); Probability of Failure on Demand (POFOD); Rate of Occurrence of Failure (ROCOF).
Robustness Time to restart after failure; percentage of events causing catastrophic data loss.
Portability Percentage of target-dependent statements; number of supported operating systems.
QUICK RECALL
  • Functional: what the system DOES (services, behaviors).
  • Non-Functional: constraints on how the system does it (Product, Organizational, External).
  • NFRs must be measurable (e.g. response time $\le 0.5$s, availability $\ge 99.9\%$).
§ 2

The Software Requirements Specification (SRS) & IEEE 830

The Software Requirements Specification (SRS) is the official statement of what the system developers should implement. It serves as a contract between customers, users, systems engineers, software developers, and quality assurance testers.

STANDARD STRUCTURE OF AN IEEE 830 SRS DOCUMENT
  1. 1. Introduction
    • 1.1 Purpose of the document
    • 1.2 Scope of the product / system
    • 1.3 Definitions, acronyms, and abbreviations
    • 1.4 References
    • 1.5 Overview of document structure
  2. 2. General Description
    • 2.1 Product perspective (relationship to other systems)
    • 2.2 Product functions (summary of major services)
    • 2.3 User characteristics and educational level
    • 2.4 General constraints (regulatory, hardware limits)
    • 2.5 Assumptions and dependencies
  3. 3. Specific Requirements
    • 3.1 External interface requirements (User, Hardware, Software, Communications)
    • 3.2 Functional requirements (organized by use case or feature mode)
    • 3.3 Performance requirements (speed, throughput, memory)
    • 3.4 Design constraints (standards, programming language)
    • 3.5 Software system attributes (reliability, security, maintainability)
  4. 4. Appendices & Index

Attributes of a High-Quality SRS

  • Correct: Every requirement accurately reflects customer needs.
  • Unambiguous: Every requirement has only one single possible interpretation.
  • Complete: Covers all significant requirements, inputs, responses, and error conditions.
  • Consistent: No conflicting statements (e.g. one section states blue background while another states green).
  • Verifiable (Testable): A cost-effective inspection or automated test can prove compliance.
  • Modifiable: Structure allows changes without destroying the document hierarchy.
  • Traceable: Each requirement has a unique identifier linked to its origin and downstream code/tests.
QUICK RECALL
  • IEEE 830 standard divides SRS into: (1) Introduction, (2) General Description, (3) Specific Requirements.
  • Key SRS qualities: Unambiguous, Complete, Consistent, Verifiable, Traceable.
§ 3

Requirements Engineering Processes & Traceability (RTM)

The requirements engineering process is an iterative spiral comprising four major sub-activities: Feasibility study, Elicitation & analysis, Specification, and Validation.

1
Requirements Elicitation & Analysis: Technical staff collaborate with customers to discover the application domain, what services the system should provide, and operational constraints. Techniques include:
  • Interviews: Closed (pre-set questions) and open (exploratory discussions).
  • Scenarios & User Stories: Concrete stories of how a system is used in everyday workflows.
  • Ethnography (Observation): Analysts observe actual workplace operations to uncover tacit social and implicit organizational requirements.
2
Requirements Validation: Demonstrating that requirements define the system the customer truly wants. Techniques: Formal requirements reviews, Prototyping, and Test-case generation.
3
Requirements Management & Change Control: Managing changes to agreed requirements as the business evolves. Includes formal change request forms, impact analysis, and tracking via a Requirements Traceability Matrix (RTM).

Requirements Traceability Matrix (RTM)

An RTM is a grid linking each unique user requirement to its architectural module, design element, and automated verification test cases:

Requirement ID Requirement Description Architectural Module Verification Test Case(s) Compliance Status
REQ-01 User Multi-Factor Authentication (OTP via SMS) AuthModule TC-01, TC-02 Verified / Pass
REQ-02 Course Catalog Filtering by Department CatalogModule TC-03 Verified / Pass
REQ-03 Shopping Cart Seat Reservation Hold (10 min) CartModule TC-04 Verified / Pass
REQ-04 Payment Gateway Integration (Stripe/PayPal) PaymentModule TC-05, TC-06 Verified / Pass
REQ-05 Automated Registration Confirmation Email NotificationModule TC-07 Verified / Pass
REQ-06 Semester Grade Report PDF Export ReportingModule TC-08 Verified / Pass
QUICK RECALL
  • Elicitation techniques: Interviews, Scenarios, Use cases, Ethnography (passive observation).
  • Validation: Reviews, Prototyping, Test-case generation.
  • RTM links Requirements → Architecture → Code → Test Cases.
§ 4

Context & Interaction Models: Use Case Diagrams

System modeling uses graphical notations (principally the Unified Modeling Language - UML) to represent different perspectives of a system: External context, Interaction, Structural, and Behavioral.

Use Case Modeling

A Use Case describes an interaction between the system and external actors (humans or external hardware/software systems). Actors are represented by stick figures, use cases by horizontal ellipses, and relationships by solid or dashed arrows.

Use Case Diagram for Student Course Registration
INCLUDE VS EXTEND RELATIONSHIPS IN USE CASES
  • <<include>>: Mandatory behavior. The base use case always executes the included use case as an essential sub-step (e.g. Registering for a course <<include>> Verifying Prerequisites).
  • <<extend>>: Optional / Conditional behavior. The extension use case is executed only under specific circumstances governed by an extension point (e.g. Booking flight ticket <<extend>> Purchasing Travel Insurance).
QUICK RECALL
  • Actor: external entity interacting with system (stick figure).
  • Use case: specific service / interaction sequence (ellipse).
  • <<include>> is mandatory sub-routine; <<extend>> is optional/conditional.

§ 6

Structural Models: UML Class Diagrams

Structural models display the static organization of a system in terms of components, classes, and relationships. The UML Class Diagram is the premier structural modeling tool.

Relationship UML Notation Semantic Meaning & Lifecycle Binding
Association Solid line with label / arrow General structural relationship indicating objects know about each other ("uses-a").
Aggregation Hollow diamond at container end "Has-a" part-whole relationship. Weak ownership: parts can exist independently of the whole (e.g. Department & Professors).
Composition Filled black diamond at container end "Contains-a" part-whole relationship. Strong ownership: parts cannot exist without the whole; if container is destroyed, parts are destroyed (e.g. Building & Rooms).
Generalization (Inheritance) Hollow triangle pointing to superclass "Is-a" relationship where subclass inherits attributes and operations from superclass (e.g. Student extends Person).
QUICK RECALL
  • Aggregation (hollow diamond): weak ownership (parts survive without whole).
  • Composition (filled black diamond): strong ownership (parts destroyed with whole).
  • Generalization (hollow triangle): inheritance ("is-a").
§ 7

Behavioral Models: Activity & State Machine Diagrams

Behavioral models describe what happens when a system responds to internal or external stimuli. They model the dynamic operational control flow of the application.

1. Activity Diagrams

Model the procedural flow of business logic and workflows. Key notations:

  • Initial Node: Solid black circle.
  • Action State: Rounded rectangle representing a unit of work.
  • Decision Node: Diamond with outgoing guarded branches ($[\text{condition}]$).
  • Forks and Joins: Horizontal/vertical solid bars used to represent concurrent parallel threads of execution (a fork splits one flow into multiple; a join waits for all concurrent flows to arrive).
  • Swimlanes: Vertical columns grouping activities by organizational role (e.g. Customer, OrderDesk, Inventory, Warehouse).

2. State Machine Diagrams (Statecharts)

Model the life cycle of a reactive object across discrete states in response to events.

STATE TRANSITION LABELING NOTATION $$\mathbf{\text{Event [Guard Condition] / Action}}$$

Example: $\text{CardInserted [PIN\_Valid] / DisplayAccountMenu()}$

QUICK RECALL
  • Activity Diagram: procedural workflows; forks/joins handle parallel concurrency; swimlanes assign responsibilities.
  • State Machine: states and transitions for reactive objects ($\text{Event [Guard] / Action}$).
§ 8

Model-Driven Engineering (MDE & MDA)

Model-Driven Engineering (MDE) is an approach to software development in which models, rather than source code, are the principal outputs of the development process. Programs that execute on hardware platforms are then generated automatically from these models.

Model Layer Model Name Level of Abstraction & Contents
Layer 1 (Top) Computation Independent Model (CIM) Models business domain concepts without any reference to system implementation (sometimes called a Domain Model).
Layer 2 (Middle) Platform Independent Model (PIM) Models the operational behavior of the software system without committing to any specific implementation technology or target platform.
Layer 3 (Bottom) Platform Specific Model (PSM) Transforms the PIM into specific implementation environments (e.g. Java Spring Boot + PostgreSQL, or .NET C# + SQL Server) using automated translator tools.
QUICK RECALL
  • MDA 3 Tiers: CIM → PIM → PSM.
  • CIM = business domain concepts.
  • PIM = system behavior independent of hardware/OS.
  • PSM = concrete technology implementation for code generation.

Important Examination Questions

2-Mark Questions (Short Answer)

2M Distinguish between functional and non-functional requirements.

Answer: Functional requirements state the specific services, functions, and behaviors the system must deliver. Non-functional requirements specify constraints on these services (e.g. performance speed, security standards, availability, and regulatory compliance).

2M Differentiate between `<>` and `<>` in use case diagrams.

Answer: An <<include>> relationship indicates mandatory behavior that is always executed as an integral part of the base use case. An <<extend>> relationship represents optional or conditional behavior executed only under specific extension point conditions.

2M What is a Requirements Traceability Matrix (RTM)?

Answer: An RTM is a table that links every individual user requirement from its initial inception through system architecture modules, source code files, and automated verification test cases, ensuring complete test coverage and tracking change impact.

5-Mark Questions (Medium Length)

5M Explain the structure of an SRS document according to the IEEE 830 standard.

Answer: Outline the three main sections: (1) Introduction (purpose, scope, definitions), (2) General Description (product perspective, functions, user characteristics, constraints), and (3) Specific Requirements (external interfaces, functional requirements, performance, design constraints), as detailed in Section 2.

5M Compare aggregation and composition in UML class diagrams with examples.

Answer:

  • Aggregation (hollow diamond): Represents a weak part-whole relationship. The contained objects can exist independently of the whole. Example: A Department has Professors; if the Department closes, Professors still exist.
  • Composition (filled black diamond): Represents strong ownership. The parts are created and destroyed with the container. Example: A Building has Rooms; if the Building is demolished, the Rooms cease to exist.

Practice Problems with Hidden Answers

PRACTICE 1 • AVAILABILITY CALCULATION

A cloud server has an MTBF of 500 hours and an MTTR of 2 hours. Calculate its availability percentage.

Show Step-by-Step Solution

Formula: $\text{Availability } A = \frac{\text{MTBF}}{\text{MTBF} + \text{MTTR}}$

$$A = \frac{500}{500 + 2} = \frac{500}{502} \approx 0.996016 = \mathbf{99.602\%}$$
PRACTICE 2 • NFR CLASSIFICATION

Classify the requirement: "The system must conform to ISO 9001 quality audit documentation."

Show Step-by-Step Solution

Organizational Requirement • Development Standards. It dictates the organizational development and auditing process rather than the functional runtime behavior of the software product.
