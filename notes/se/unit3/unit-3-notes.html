§ 1

Architectural Design Decisions & Non-Functional Influences

Software Architecture is the fundamental structure of a software system, comprising software components, the externally visible properties of those components, and the relationships among them. Architectural design is the critical link between requirements and detailed module design.

WHY SOFTWARE ARCHITECTURE MATTERS
  1. Stakeholder Communication: Represents a high-level abstraction understandable by non-technical clients, managers, and engineers.
  2. System Analysis: Determines whether the system can meet critical non-functional requirements (performance, reliability, security).
  3. Large-Scale Reuse: Architectural styles and patterns can be reused across an entire product line or company portfolio.

Non-Functional Quality Attributes Influencing Architecture

Non-Functional Attribute Architectural Strategy / Structural Decision
Performance Localize critical operations in small, dedicated subsystems; minimize cross-boundary communications; use caching and coarse-grained components.
Security Adopt a layered architecture with innermost layers protecting core data; enforce multi-layer perimeter authentication and validation barriers.
Safety Localize safety-critical functions into distinct, isolated modules; decouple safety monitors from general business processing.
Availability Incorporate redundant components, load-balanced clusters, and automatic failover hot-standby servers.
Maintainability Use fine-grained, self-contained, loosely coupled components; isolate business logic from presentation and database tiers.
QUICK RECALL
  • Architecture is the high-level structural blueprint linking requirements to code.
  • Architecture is driven primarily by Non-Functional Requirements (performance, security, safety, maintainability).
§ 2

Kruchten's 4+1 View Model of Architecture

A single architectural diagram cannot capture all facets of a system. Philippe Kruchten proposed the 4+1 View Model, which decomposes system architecture into four separate visual perspectives, unified by a central set of use cases.

Architectural View Primary Stakeholder Focus What it Shows / UML Diagrams Used
1. Logical View End users, business analysts, systems analysts Decomposition of the system into conceptual abstractions (classes, packages, interfaces). Shows domain object models. (Class Diagrams, Object Diagrams)
2. Process View Integrators, performance engineers Shows concurrency, runtime processes, threads, synchronization, and inter-process communication. (Activity Diagrams, State Machine Diagrams)
3. Development View Programmers, software managers Shows software organization in the development environment (source files, packages, libraries, subsystems). (Component Diagrams, Package Diagrams)
4. Physical View Systems engineers, network admins, devops Shows the hardware execution topology: how software components are mapped onto physical servers, CPUs, and network links. (Deployment Diagrams)
+1 Scenarios (Use Cases) All stakeholders The unifying glue. A small set of critical use cases illustrate how the four views work together to fulfill system requirements. (Use Case Diagrams)
QUICK RECALL
  • 4+1 Views: Logical, Process, Development, Physical, unified by Scenarios (+1).
  • Logical = classes/objects; Process = concurrency/threads; Development = source code/packages; Physical = deployment hardware.
§ 3

Architectural Patterns: MVC & Layered Architecture

An architectural pattern is a stylized description of good design practice that has been tried and tested in different environments. It establishes the fundamental structural organization schema for a software system.

1. The Model-View-Controller (MVC) Pattern

Separates presentation and user interaction from the underlying system data and business logic.

  • Model: Manages the data, business rules, and state of the application. Dispatches notifications when data changes.
  • View: Defines and renders the user interface display (HTML, mobile UI, desktop GUI). Observes the model.
  • Controller: Handles user inputs (clicks, keypresses, HTTP requests), translates them into model updates or view changes.
Model-View-Controller (MVC) Architecture

Strengths: Allows multiple independent views of the exact same data (e.g. table view and pie chart); changes to UI do not affect model.
Weaknesses: Added architectural complexity for simple user interfaces.

2. Layered Architecture Pattern

Organizes the system into hierarchical layers, with each layer providing services to the layer immediately above it and consuming services from the layer below it.

  • User Interface Layer: Handles browser UI, web pages, or mobile views.
  • Application / Business Logic Layer: Implements workflows, transaction rules, domain logic.
  • Core Domain / Database Access Layer: Object-relational mapping (ORM), data persistence queries.
  • System Software Layer: Operating system, database engines, hardware abstraction.

Strengths: Supports incremental development; changes to one layer affect only that layer if interface contracts remain stable.
Weaknesses: Clean separation can be hard in practice; performance overhead from passing data through multiple sequential boundaries.

QUICK RECALL
  • MVC: Model (data), View (UI), Controller (events). Decouples data from presentation.
  • Layered: Hierarchical stack (UI → Business Logic → Persistence → Database). Clean separation.
§ 4

Repository, Client-Server & Pipe-and-Filter Patterns

Three additional foundational patterns frequently appear in enterprise and systems architecture: Repository, Client-Server, and Pipe-and-Filter.

Pattern Name Architectural Mechanism Major Advantages Disadvantages & Limitations
Repository Pattern All shared system data is managed in a central repository accessible to all independent subsystems. Subsystems do not communicate directly. Efficient for sharing large volumes of complex data (e.g. IDEs like Eclipse, CAD tool suites, hospital records). Single point of failure: If the central repository crashes, all subsystems halt. Data schema evolution is difficult.
Client-Server Pattern System functionality is organized into services. Servers provide dedicated services; clients request services over a network protocol. Distributed execution over networks; servers can be replicated across clusters transparently. Performance unpredictable due to network latency; server load balancing required under heavy traffic.
Pipe-and-Filter Pattern Processing is organized so that each processing component (Filter) takes input data, transforms it, and produces output data sent to the next component via a Pipe. Intuitive flow modeling; filters can be reused or executed concurrently in parallel (e.g. Unix pipelines, audio processing). Format overhead (data must be parsed and serialized between each pipe); interactive systems cannot easily use it.
QUICK RECALL
  • Repository: Central database for all tools (e.g. IDEs). Single point of failure.
  • Client-Server: Decoupled service providers and service requesters over network.
  • Pipe-and-Filter: Sequential data transformations (e.g. Unix pipes, compilers).
§ 5

Application Architectures

Application architectures are standardized architectural frameworks designed for specific business application types. Two dominant classes are Transaction Processing Systems and Language Processing Systems.

1. Transaction Processing Systems (TPS)

Designed to process user requests for information from a database, update the database, and return results. Transactions must adhere to the ACID properties (Atomicity, Consistency, Isolation, Durability).

Structure: User requests pass through an I/O processing layer (validation and formatting), through a transaction manager, down into database updates.

2. Language Processing Systems (LPS)

Translates a formal natural or programming language into an alternative machine-readable format. Implemented using the Pipe-and-Filter architecture:

1
Lexical Analyzer (Lexer): Converts input source characters into atomic tokens.
2
Syntax Analyzer (Parser): Checks grammatical syntax and builds a Parse Tree / Abstract Syntax Tree (AST).
3
Semantic Analyzer: Performs type checking and binds symbols in a Symbol Table.
4
Code Generator: Synthesizes target assembly, bytecode, or native machine code.
QUICK RECALL
  • Transaction Processing: ACID guarantees for database queries/updates.
  • Language Processing: Compilers use Pipe-and-Filter: Lexer → Parser → Semantic → Code Gen.
§ 6

Object-Oriented Design Using the UML

Object-Oriented design is an iterative engineering process that models a software system as a collection of collaborating objects, each encapsulating state and behavior.

1
Understand the System Context & Interactions: Establish the boundaries of the system and model external actor interactions using Use Case diagrams.
2
Design the System Architecture: Select an overarching architectural pattern (e.g. Layered or MVC) to partition functionality into major subsystems.
3
Identify Principal System Objects: Use grammatical analysis of the requirements specification (nouns indicate candidate classes; verbs indicate candidate methods) to identify domain objects.
4
Develop Design Models: Construct static structural models (Class Diagrams) and dynamic behavioral models (Sequence Diagrams, State Machine Diagrams).
5
Specify Object Interfaces: Define unambiguous API method signatures (operation names, parameter types, return values, exception throws) so components can be programmed concurrently.
QUICK RECALL
  • 5 Steps: (1) System context → (2) Architecture → (3) Identify objects (nouns) → (4) Design models → (5) Specify interfaces.
§ 7

Gang of Four (GoF) Design Patterns

Design patterns are reusable solutions to commonly occurring problems in software design. In 1994, Erich Gamma, Richard Helm, Ralph Johnson, and John Vlissides ("The Gang of Four") categorized 23 classical patterns into three families: Creational, Structural, and Behavioral.

Category Pattern Name Intent & Problem Solved
Creational
(Object creation mechanisms)		 Singleton Pattern Ensure a class has only one single instance and provide a global point of access to it (e.g. Database Connection Pool, Logger, Thread Pool).
Factory Method Define an interface for creating an object, but let subclasses decide which class to instantiate. Defers instantiation to subclasses.
Structural
(Class & object composition)		 Adapter Pattern Convert the interface of a class into another interface clients expect. Lets classes work together that couldn't otherwise because of incompatible interfaces.
Behavioral
(Algorithms & assignments of responsibility)		 Observer Pattern
(Publish-Subscribe)		 Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.

Singleton Pattern & Observer Pattern Implementations

1. Singleton Pattern Implementation (Thread-Safe Python):

class DatabaseConnectionPool:
    _instance = None

    def __new__(cls):
        # Enforce exactly one instance across entire application
        if cls._instance is None:
            cls._instance = super(DatabaseConnectionPool, cls).__new__(cls)
            cls._instance.connections = 10
            cls._instance.active_connections = 0
        return cls._instance

# Verification:
pool1 = DatabaseConnectionPool()
pool2 = DatabaseConnectionPool()
print(pool1 is pool2)  # Output: True (Identical memory reference!)

2. Observer Pattern Implementation (Publish-Subscribe):

class WeatherStationSubject:
    def __init__(self):
        self._observers = []
        self._temperature = None

    def attach(self, observer):
        self._observers.append(observer)

    def detach(self, observer):
        self._observers.remove(observer)

    def set_temperature(self, temp):
        self._temperature = temp
        self.notify_all()

    def notify_all(self):
        for observer in self._observers:
            observer.update(self._temperature)

class PhoneDisplayObserver:
    def __init__(self, user_name):
        self.user_name = user_name

    def update(self, temperature):
        print(f"[{self.user_name}] Notification: Current Temp is {temperature}°C")

# Usage:
station = WeatherStationSubject()
display_alice = PhoneDisplayObserver("Alice")
display_bob = PhoneDisplayObserver("Bob")

station.attach(display_alice)
station.attach(display_bob)
station.set_temperature(28)  # Both Alice and Bob receive automated updates!
The Observer pattern cleanly decouples the Subject (data producer) from the Observers (data consumers), satisfying the Open-Closed Principle!
QUICK RECALL
  • 3 GoF Families: Creational (creation), Structural (composition), Behavioral (interaction).
  • Singleton: exactly one instance with global access point.
  • Observer: 1-to-many publish-subscribe dependency; updates all listeners on state change.
§ 8

Open Source Software Licensing Models

Modern software engineering heavily leverages open-source software (OSS). Engineers must understand open-source licenses to avoid legal liabilities and unintended proprietary disclosure.

License Type Common Examples Core Terms & Intellectual Property Obligations
Permissive Licenses MIT, BSD, Apache 2.0 Software can be used, modified, and redistributed freely in commercial proprietary products without requiring source code disclosure. Apache 2.0 explicitly grants patent rights.
Strict Copyleft (Viral) GNU GPL (General Public License v2/v3) If you modify or combine GPL code with your proprietary code, the entire derived product must also be licensed under the GPL and made open-source. Cannot be kept closed-source.
Weak Copyleft GNU LGPL (Lesser GPL), MPL (Mozilla) Modifications to the library itself must remain open-source. However, proprietary commercial applications can link to the unmodified library without having to open-source the parent app.
QUICK RECALL
  • Permissive (MIT, Apache): free commercial use without opening proprietary code.
  • Copyleft (GPL): requires any derivative software to be open-sourced under the GPL.
  • Weak copyleft (LGPL): allows proprietary linking if the library itself is unbundled.

2M Distinguish between MIT license and GNU GPL license.

Answer: The MIT license is permissive and allows software to be incorporated into proprietary closed-source products without releasing code. The GNU GPL is copyleft and mandates that any derivative software must also be licensed under the GPL and made open source.

Practice Problems with Hidden Answers

PRACTICE 1 • PATTERN SELECTION

Which architectural pattern is best suited for an Integrated Development Environment (IDE) like VS Code or Eclipse? Justify.

Show Step-by-Step Solution

The Repository Architecture Pattern.

An IDE comprises diverse independent tools (compiler, syntax highlighter, debugger, refactoring engine, git tracker) that must all read and modify the same complex data structures (Abstract Syntax Trees, file buffers, project configuration). Storing these centrally in an in-memory repository allows all tools to interact without direct point-to-point coupling.

PRACTICE 2 • DESIGN PATTERNS

In an online multiplayer game, when a player's health reaches 0, the audio engine plays a death sound, the UI displays "Game Over", and the leaderboard updates. Which GoF pattern should be used?

Show Step-by-Step Solution

The Observer Pattern.

The Player character acts as the Subject. The AudioEngine, UIManager, and LeaderboardService act as Observers. When the player dies, the Subject calls notify_all() without needing to know any concrete details about the audio or leaderboard subsystems.
