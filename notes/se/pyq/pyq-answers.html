📖 Theory Link: Unit 1 § 1

Define Software Engineering. How is it more than 'just programming'? Consider a client has a vague idea of their requirements and expects them to change frequently. Which process model would you recommend and why?

Model Exam Answer

Software Engineering is an engineering discipline concerned with all aspects of software production from the earliest stages of system specification through to maintaining and evolving the system after it has gone into use (Sommerville, Ch. 1).

Why More Than Programming:

  • Systematic Lifecycle: Programming is merely the coding phase. Software engineering encompasses requirements analysis, architectural design, verification & validation, deployment, configuration management, and ongoing software evolution.
  • Socio-Technical & Economic Constraints: Professional software must be developed on schedule, within organizational budgets, and adhere to strict quality attributes (maintainability, dependability, efficiency, and usability).
  • Team-Based & Industrial Scale: Programming is often individual or small-scale; software engineering provides the organizational framework, version control, automated testing, and governance needed for large teams building complex, long-lived systems.

Recommendation Case:

Scenario: Client with vague, emerging requirements expecting frequent changes.

Recommended Model: Agile Incremental Development / Extreme Programming (XP) or Scrum (or Evolutionary Prototyping).

Justification:
  • Rapid Feedback Cycles: Developing in small 1–2 week sprints/iterations allows the customer to interact with working software increments, helping them clarify their vague vision early.
  • Low Cost of Change: In waterfall, changing requirements mid-stream causes catastrophic rework of specification and architecture documents. In agile, the Product Backlog is reprioritized at every sprint boundary without penalty.
  • Customer Collaboration over Contract Negotiation: Continuous customer involvement ensures that as the client's understanding evolves, the software directly aligns with actual business needs.
  • Continuous Integration & Automated Testing: Ensures regression defects are caught immediately as features are adapted.
Source: Sommerville 10e, Chapter 1 (pp. 18-24) & Chapter 2 (pp. 44-50)

📖 Theory Link: Unit 1 § 4

With a neat diagram, explain in detail about the Waterfall process model for software development. Identify its advantages and limitations.

Model Exam Answer

The Waterfall Model (Classic Life Cycle) is a plan-driven software process model where each fundamental process activity is organized into separate, sequential phases, with the output of one phase serving as the formal baselined input to the next.

Phases:

  • 1. Requirements Definition: System services, constraints, and goals are established in consultation with stakeholders and formally documented in an SRS.
  • 2. System and Software Design: Allocates requirements to hardware/software systems; establishes overall software architecture and data structures.
  • 3. Implementation and Unit Testing: Software design is realized as sets of programs or program units; verified through unit testing.
  • 4. Integration and System Testing: Individual program units are integrated and tested as a complete system to ensure software requirements are met; followed by acceptance testing.
  • 5. Operation and Maintenance: The system is deployed into operational use; includes bug fixes, enhancing capabilities, and adapting to new hardware.

Advantages:

  • Clear, disciplined milestones and deliverables at each stage make project management and progress tracking straightforward.
  • Extensive upfront documentation ensures team members have a shared understanding and facilitates knowledge transfer.
  • Well suited for stable, well-understood systems (e.g. large infrastructure, aerospace, defense contracts).

Limitations:

  • Inflexible Partitioning: Difficult to accommodate changing customer requirements once an earlier stage is frozen.
  • Late Software Delivery: Working software is produced only late in the lifecycle; major design errors may remain hidden until integration.
  • High Cost of Rework: An error in requirements discovered during system testing costs up to 100x more to fix than if identified early.
Source: Sommerville 10e, Chapter 2.1 (pp. 44-46)

📖 Theory Link: Unit 1 § 4

Describe and elaborate the four distinct phases of the Rational Unified Process (RUP), with a neat diagram.

Model Exam Answer

The Rational Unified Process (RUP) is a modern generic process framework that combines elements of all generic process models. It has two dimensions: dynamic (lifecycle phases over time) and static (workflows/disciplines across iterations).

Four Phases:

  • 1. Inception Phase: Establish the business case, project scope, identify all external entities (actors), define major use cases at a high level, and assess business viability and financial risks.
  • 2. Elaboration Phase: Deepen understanding of problem domain; establish an architectural baseline; identify and eliminate the highest project risks; produce the executable architecture.
  • 3. Construction Phase: System design, programming, and unit/integration testing. Components are implemented, integrated into the architecture, and tested against use cases; produces the first external beta release.
  • 4. Transition Phase: Move system from development environment to operational user environment. Involves beta testing, user training, defect correction, and product rollout.

Key Practices:

  • Develop iteratively with user feedback.
  • Manage requirements through use case driven models.
  • Use component-based architectures.
  • Visually model software using Unified Modeling Language (UML).
  • Continuously verify quality and manage changes.
Source: Sommerville 10e, Chapter 2.4 (pp. 57-60)

📖 Theory Link: Unit 1 § 7

What is the need for Extreme Programming (XP)? Draw and describe the Extreme Programming release/iteration cycle, highlighting key XP practices.

Model Exam Answer

Need For Xp:

Traditional methods assumed changes late in development were prohibitively expensive. Extreme Programming (XP) was created by Kent Beck to take recognized good development practices (e.g. testing, reviews, integration) and push them to 'extreme' levels to make software development highly responsive to customer needs while maintaining code quality.

Xp Cycle Description:

  • 1. User Stories: Customer requirements are written on story cards by the customer.
  • 2. Release Planning: Team and customer prioritize stories into the next release schedule and break stories into developmental tasks.
  • 3. Iteration Development: In 1-2 week cycles, developers implement tasks using Pair Programming and Test-Driven Development.
  • 4. Acceptance Tests: Customer-defined automated tests verify completed stories.
  • 5. Software Release: Delivered frequently to users; feedback immediately feeds next user stories.

Core Practices:

  • Test-Driven Development (TDD): Tests are written *before* code; code is only written to make tests pass.
  • Pair Programming: Two programmers work together at one workstation (driver and navigator), providing continuous code review and shared ownership.
  • Refactoring: Continually improving system structure without altering external behavior.
  • Continuous Integration: Code is checked in and integrated multiple times a day with automated regression suites.
Source: Sommerville 10e, Chapter 3.2 (pp. 77-83)

📖 Theory Link: Unit 1 § 2

List out the different ethical responsibilities of the software engineering profession. State the eight principles of the ACM/IEEE-CS Code of Ethics.

Model Exam Answer

Software engineers must behave in an honest and ethically responsible manner, not merely follow the law. Technical competence must be joined with ethical integrity because software systems directly impact public safety, privacy, and economic well-being.

Professional Responsibilities:

  • Confidentiality: Respect client/employer confidentiality regardless of whether a formal non-disclosure agreement was signed.
  • Competence: Do not misrepresent level of competence; do not knowingly accept work outside personal competence.
  • Intellectual Property Rights: Respect patents, copyrights, and open-source licenses; never use unauthorized software.
  • Computer Misuse: Never use technical abilities to breach security, deploy malware, or access private systems unauthorized.

Eight Principles:

  • 1. PUBLIC: Act consistently with the public interest as paramount.
  • 2. CLIENT AND EMPLOYER: Act in a manner that is in the best interests of client and employer, consistent with public interest.
  • 3. PRODUCT: Ensure products and related modifications meet the highest professional standards possible.
  • 4. JUDGMENT: Maintain integrity and independence in professional judgment.
  • 5. MANAGEMENT: Managers and leaders shall subscribe to and promote an ethical approach to software management.
  • 6. PROFESSION: Advance the integrity and reputation of the profession consistent with public interest.
  • 7. COLLEAGUES: Be fair to and supportive of colleagues.
  • 8. SELF: Participate in lifelong learning regarding the practice of their profession and promote an ethical approach.
Source: Sommerville 10e, Chapter 1.3 (pp. 28-31)

📖 Theory Link: Unit 1 § 5

With a neat diagram explain Boehm's Spiral Model. Discuss its risk-driven nature, four quadrants, and its advantages over the waterfall model.

Model Exam Answer

Boehm's Spiral Model is a risk-driven software process framework where the development lifecycle is represented as a spiral, rather than a sequence of activities with backtracking. Each loop represents a phase of the process.

Four Quadrants:

  • 1. Objective Setting (Quadrant 1): Specific objectives for the phase are identified. Constraints on processes and products are defined, and a detailed management plan is drawn up.
  • 2. Risk Assessment and Reduction (Quadrant 2): For each identified project risk, a detailed analysis is carried out. Steps are taken to reduce risks (e.g. prototyping, simulations, benchmarking).
  • 3. Development and Validation (Quadrant 3): A development model for the system is chosen based on remaining risks (e.g. waterfall if low risk, evolutionary prototype if UX risk, etc.). The increment is built and validated.
  • 4. Planning (Quadrant 4): The project is reviewed and a decision is made whether to continue with a further loop of the spiral. Plans are drawn up for the next phase.

Advantages Over Waterfall:

  • Explicit risk management avoids unexpected project catastrophes.
  • Accommodates evolving requirements through successive spiral loops.
  • Allows different sub-models to be selected within different phases.
Source: Sommerville 10e, Chapter 2.3.2 (pp. 55-57)

With a neat diagram, explain the activity model of the Insulin Pump control system. Why is this considered a safety-critical system?

Model Exam Answer

The Insulin Pump is a safety-critical embedded system used to regulate blood sugar in patients with Type 1 diabetes. It measures micro-current blood glucose levels, computes insulin requirement, and drives a pump micro-motor.

Activity Steps:

  • 1. Read blood sensor output.
  • 2. Calculate blood sugar level and rate of change.
  • 3. Compute required insulin dose.
  • 4. Run safety check: ensure dose <= maximum safe single bolus.
  • 5. Command needle pump actuator to deliver computed units.
  • 6. Log delivery timestamp and insulin remaining.
  • 7. Wait for scheduled sampling interval (e.g. 10 minutes).
It is safety-critical because failure can cause death: delivering too little insulin leads to hyper-glycaemic coma; delivering an overdose leads to fatal hypo-glycaemia. The system must never fail silently and must run fail-safe self-diagnostics.

Differentiate between Functional and Non-Functional Requirements (NFRs). Provide two examples of each for an e-commerce website and develop a list of NFRs for a real-time banking application.

Model Exam Answer

Definitions:

Functional: Functional Requirements describe the specific services, functions, and behaviors the system must provide, detailing how the system should react to particular inputs and how it should behave in specific situations.

Non Functional: Non-Functional Requirements (NFRs) are constraints on the services or functions offered by the system. They include performance constraints, reliability, availability, security, regulatory standards, and development toolchain constraints.

Comparison Table:

Headers:
  • Dimension
  • Functional Requirements
  • Non-Functional Requirements

  • ['Scope', 'Individual features or sub-functions.', 'System-wide properties and emergent characteristics.']
  • ['Focus', 'What the system should DO.', 'How well or under what constraints the system PERFORMS.']
  • ['Verification', 'Tested via functional/unit test cases.', 'Tested via load, stress, security, and benchmark tests.']
  • ['Failure Consequence', 'A specific function is disabled or unavailable.', 'Whole system may be rendered unusable or legally uncompliant.']

Ecommerce Examples:

Functional:
  • 1. The user shall be able to search products by keyword, category, and price range.
  • 2. The system shall allow registered users to add items to a cart and pay via credit card, UPI, or net banking.
Non Functional:
  • 1. Performance: The product search results page shall load within 1.5 seconds for up to 10,000 concurrent users.
  • 2. Security: All credit card transactions must comply with PCI-DSS 3.2 and all customer data must be encrypted at rest using AES-256.

Banking Nfrs:

  • Availability: System uptime must be >= 99.99% (maximum 52 minutes unplanned downtime per year).
  • Transaction Latency: Fund transfers via IMPS/NEFT must complete and respond within 2.0 seconds.
  • Security: Multi-factor authentication (MFA) required for transfers > INR 10,000; session timeout after 3 minutes of inactivity.
  • Auditability: Immutable audit logs for all monetary transactions retained for 10 years per RBI regulations.

📖 Theory Link: Unit 2 § 3

List and briefly explain the requirement validation process and the five different checks carried out during validation.

Model Exam Answer

Requirements Validation is the process of checking that requirements actually define the system that the customer really wants. Discovering requirements errors at this stage saves astronomical rework costs later in the development cycle.

Five Checks:

  • 1. Validity Checks: Does the system provide the functions which best support the customer's real operational needs?
  • 2. Consistency Checks: Requirements in the document should not conflict (e.g. one section stating 24/7 availability while another stating nightly 4-hour maintenance shutdown).
  • 3. Completeness Checks: The document should include all requirements and constraints requested by the user, covering all normal and exception cases.
  • 4. Realism Checks: Can the requirements actually be implemented using known technologies, within budget and schedule constraints?
  • 5. Verifiability Checks: Can the requirements be objectively tested? Every requirement must be phrased so that a software tester can design an unambiguous pass/fail test.

Validation Techniques:

  • Requirements Reviews (Walkthroughs): Systematic manual analysis by developers, customers, and contractors.
  • Prototyping: Building an executable model to test user reaction and validate assumptions.
  • Test-Case Generation: If creating a test case is impossible for a requirement, it is ambiguous and must be rewritten.
Source: Sommerville 10e, Chapter 4.5 (pp. 123-125)

📖 Theory Link: Unit 2 § 3

What is Ethnography? Illustrate with a diagram how combining Ethnography and Prototyping helps the requirements discovery process.

Model Exam Answer

Ethnography is an observational technique where an analyst immerses themselves in the actual working environment where the system is to be used, watching the day-to-day work and noting how people actually collaborate and use information.

Why Ethnography Matters:

  • Discovers implicit (tacit) requirements that workers cannot articulate because procedures are second nature to them.
  • Identifies social and organizational factors that determine whether a software system will actually be accepted or resisted in practice.
  • Limitation: Ethnography reveals how people currently work, but cannot innovate or establish new organizational structures.

Combining With Prototyping:

Prototyping is focused and forward-looking, but can overlook subtle workplace dynamics. When combined:
- Ethnography informs the early prototype by grounding it in real workplace habits.
- Prototyping directs the ethnographer's focus to specific workflows and provides a concrete artifact for users to critique.

Source: Sommerville 10e, Chapter 4.4.4 (pp. 120-123)

📖 Theory Link: Unit 2 § 2

What are the problems with using Natural Language for specifying systems requirements? Explain how Structured Natural Language specifications overcome these problems.

Model Exam Answer

Problems With Natural Language:

  • 1. Ambiguity & Lack of Clarity: Authors mistakenly assume readers share their implicit context, causing words to be interpreted differently by developers and clients.
  • 2. Requirements Confusion: Functional requirements, non-functional requirements, project goals, and design details become mixed up in the same paragraph.
  • 3. Requirements Amalgamation: Multiple distinct requirements are lumped together into a single sprawling sentence.
  • 4. Over-Flexibility: The same concept can be phrased in ten different ways, making automated verification or cross-referencing impossible.

Structured Natural Language Solution:

  • Uses a standard form/template with mandatory predefined fields to write requirements.
  • Standard Fields: Function Name, Description, Inputs (source & format), Outputs (destination & rate), Pre-conditions, Post-conditions, Side-effects, Exceptions.
  • Maintains readability for non-technical clients while enforcing rigor, completeness, and consistency for engineers.
Source: Sommerville 10e, Chapter 4.3 (pp. 112-116)

📖 Theory Link: Unit 2 § 2

Explain the structure of a Software Requirements Specification (SRS) document according to IEEE 830 standard and highlight the characteristics of a good SRS document.

Model Exam Answer

The Software Requirements Specification (SRS) is the official statement of what the system developers should implement. It serves as a contract between customer and developer.

Ieee 830 Structure:

  • 1. Introduction: 1.1 Purpose, 1.2 Scope, 1.3 Definitions/Acronyms, 1.4 References, 1.5 Overview.
  • 2. Overall Description: 2.1 Product Perspective, 2.2 Product Functions, 2.3 User Characteristics, 2.4 General Constraints, 2.5 Assumptions and Dependencies.
  • 3. Specific Requirements: Detailed functional requirements, non-functional requirements (performance, reliability, security), external interface requirements (user, hardware, software, communications), and design constraints.
  • 4. Appendices & Index: Hardware specs, sample input/output forms, glossary.

Characteristics Of Good Srs:

  • Correct: Every requirement stated is one that the software shall meet.
  • Unambiguous: Every requirement has only one interpretation.
  • Complete: Includes all significant requirements (inputs, outputs, exceptions).
  • Consistent: No two requirements conflict with each other.
  • Verifiable: There exists a finite, cost-effective test to verify each requirement.
  • Modifiable & Traceable: Well-structured with unique IDs so changes can be tracked easily.
Source: Sommerville 10e, Chapter 4.2 (pp. 109-112) & IEEE 830-1998

📖 Theory Link: Unit 2 § 3

With a neat diagram, explain the overall Requirements Engineering (RE) process and its primary activities.

Model Exam Answer

The Requirements Engineering Process is a structured set of activities used to discover, analyze, specify, validate, and maintain a software requirements document.

Four Primary Activities:

  • 1. Feasibility Study: Assesses whether the system contributes to business objectives, can be engineered within current tech/budget, and integrates with existing systems. Outputs a Feasibility Report.
  • 2. Requirements Elicitation and Analysis: Working with customers to discover domain info, system services, and operational constraints. Involves discovery, classification, prioritization, and negotiation.

  • 4. Requirements Validation: Checking that requirements are complete, consistent, realistic, verifiable, and conform to user desires.

System Context:

An automated traffic control system installed at a busy four-way junction with inductive loop vehicle sensors, pedestrian push-buttons, and emergency vehicle optical detectors.

With a diagram explain the principal stages of a Change Management process in Requirements Management.

Model Exam Answer

Requirements Management is the process of managing changing requirements during requirements engineering and system development. Because change is inevitable, an explicit change management process ensures controlled, cost-aware evolution.

Three Stages:

  • 1. Problem Analysis & Change Specification: Identifies problem or change proposal; checks that request is valid and not a duplicate.
  • 2. Change Analysis & Costing: Assesses impact on existing system, calculates cost in dollars and schedule delay using Traceability Matrices (RTM).
  • 3. Change Implementation: Modifies requirements document, design models, and source code; regression tests; updates version baselines.

Interaction Models show how system components interact with each other and with external actors. They model dynamic system behavior.

Sequence Diagram Elements:

  • Lifelines: Dashed vertical lines representing participating objects or actors across time (time progresses downwards).
  • Activation Bars: Tall narrow rectangles placed on lifelines showing the period during which an object is executing an operation.
  • Synchronous Message (Solid Arrow with Filled Head): Caller blocks and waits for operation to return before proceeding.
  • Asynchronous Message (Solid Line with Open Arrowhead): Caller sends message and continues execution immediately.
  • Return Message (Dashed Line with Open Arrowhead): Value or control returned from called operation.
  • Combined Fragments: Rectangular frames with operator tags like alt (if-else conditional branch), opt (optional execute if condition holds), and loop (iterative execution).
Source: Sommerville 10e, Chapter 5.2 (pp. 146-150)

Differentiate between Data-Driven (Activity) models and Event-Driven (State Machine) models. Provide a simple State Machine diagram for a Microwave Oven.

Model Exam Answer
  • Data-Driven Models (Activity Diagrams): Show the sequence of actions and processing steps involved in handling data. Best for batch processing, business data pipelines, and algorithms.
  • Event-Driven Models (State Machine Diagrams): Show how a system responds to internal and external events by transitioning between discrete system states. Essential for real-time and embedded systems.

State Machine Elements:

  • States (Rounded Rectangles): An abstraction of the system's condition (e.g. Waiting, Cooking, Door Open).
  • Transitions (Directed Arrows): Movement between states triggered by an event: Trigger [Guard] / Action.
